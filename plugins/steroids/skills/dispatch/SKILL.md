## 派活之前

### 选 CLI 和模型

- **读 `--help`**。这些 CLI 迭代很快。本文档和 `references/` 记的是问题的**形状**，
  参数和数值都带日期，调用方式以你当下看到的 help 为准。
- **用 `models`/`--help` 查当下清单，不要凭记忆**。长输出先看模型的输出上限，
  这是硬约束；跨模型交叉验证时让不同家族各审一轮。具体选型见 `references/`。
- **探活**。换 CLI、换模型、换机器之后先跑一次，几秒钟排除掉一整类「空输出」的误判：

  ```bash
  <cli> run -m <provider/model> "只回答两个字：收到" < /dev/null
  ```

### 写任务

- **默认不划只读范围，信任模型自己探索**。指出入口文件和关注点即可。
- **说清楚已经修过什么**，否则它会把你刚修完的再报一遍。
- **正反约束都写进任务本身**，不放在派发时的外围提示里，否则转交或续做时会丢。
- **要求每条发现具体到文件和函数，并说明什么输入下出什么错**。泛泛的
  「建议加异常处理」既没有验证价值，也没法判断真假。
- **并行派多个实例时给不同侧重**，否则拿回三份雷同的东西。
- **一次性给足验证上下文**。成本由往返轮数决定，不由 diff 大小决定。把已知条件、
  验收标准和验证命令放进首轮任务，让它做完一轮闭环，而不是逐轮试探。
- **写代码的任务要有可接手的检查点**。要求每完成一个可验证的小单元就提交；
  中断后已有提交能接手和定位进度，未提交的半成品容易全部损失。
- **把长网络循环从委派中拆出去**。单次工具调用有超时上限，逐条查几十个 URL 容易半途被杀。
  宿主先抓取落盘，让模型做分析与成文。
- **分批送审通常比一次送全部有效**：既避开长度墙，也让它对每一部分保持注意力。

### 准备工作目录

- **不要让两个实例同时写同一个仓库**，各给独立目录。只读任务也别放到仓库外跑，
  有些 CLI 拒读 cwd 之外的路径；复制一份快照让它在里面跑。快照是功能性安排，
  不是安全隔离，不必再加沙箱。
- **确认工作目录里的依赖可用**。新目录、新工作树、快照都是空的，测试一跑就废。
  允许联网就明确授权它安装，否则宿主先装好、要求缺包只报告。

## 跑的时候

- **后台用工具自带的机制**（如 Bash 工具的 `run_in_background`），命令末尾不要加 `&`，
  否则跑完没有任何通知，只能轮询猜。
- **续问用显式会话 ID，并等待上一进程退出**。`--continue` 只指向当前目录最近会话，
  多任务时会续错；同一 session 并发会串线。OpenCode 的判定与恢复见 `references/opencode.md`。

## 空输出时依次排除

这些 CLI 出问题时通常不报错，只是安静地什么都不输出，退出码还是 0，
看起来完全像「模型没有话说」。按下面顺序排除。

### stdin 没有关掉

零字节输出，进程一直挂着或立刻退出。命令末尾加 `< /dev/null`。
这是空输出最常见的原因，先查它。

### 权限沙箱把它拦住了

输出里有 `permission requested ... auto-rejecting` 之类的行，然后**整轮中止**，
模型不会绕开，也不会把已有结论先交出来。典型受害路径：`/tmp`、家目录下的配置、别的仓库。
排查：看 help 里有没有自动批准权限的开关；提示词里指定一个它有权写的临时目录，
并要求「即使工具调用失败也要输出报告」。

### 输入长度墙

提示词一长就只回一行标题或干脆空白。这堵墙未必在模型的上下文上限，
可能在 provider 或 CLI 这一层，配置里声明的 context 大小不作数。
不要把源码塞进提示词，让它自己去读文件；需要拆分时按文件或模块分批送。

### provider 配额耗尽

**跑到一半停下**，产出里只有过程旁白（「现在让我…」），没有最终报告；
真正的错误只在 stderr 末尾，`grep -i "quota\|limit\|exceeded"` 能看到重置时间。
重试绕不开，只能换 provider 或等重置。配额按时间窗口计，跑到一半断掉钱已经花了；
派长任务前先估量，并让它**边做边把报告写进文件**，夭折时至少拿回已写完的部分。

## 拿到结果之后

**验产物，不验转述**。报告可能说反提交归属，或声称「已修改」而文件根本没动；
结论一律回到文件、diff 和命令输出上核一遍。数字要连着产生它的命令一起看，
带路径限定的 diff 数和全仓数不是一个数。

**先复现，再修**。模型可能假设对但理由错，也可能理由对但结论过头。能写复现脚本的
写一个；写不出来的，至少手工构造一次触发条件。

**要求它证明检查会红**。「加了测试」不等于测试在看，守卫、断言同理。让它把被测物改坏、
跑红、再改回；并从被测方和调用方两侧各改一次，单侧变异往往只验证了你已经相信的事。

**注意它自陈的边界**。好的报告会说「这部分我看不到」，那正是你要自己补的地方。
