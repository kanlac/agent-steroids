# 吸收新知识 —— 把教训安放进记忆

当「学习」意味着**改变 Agent 未来的行为**、而不只是总结一份资料时，走这一篇。它覆盖两个触发场景：

- **会话末提取**——review 刚发生的一段会话，把其中的纠偏、踩坑、失败流程、样例提炼成一条可复用的教训。
- **用户中途主动要求记住某事**——用户当场说「把这个记下来 / 记进 skill / 更新源码加上这条」。

两种场景走同一套方法：**先判归属，再重构落地。**

## 第一步：先跑路由问题（这条知识该住哪）

别默认「有用就记下来」，先跑 SKILL.md 哲学里的**路由问题**——它该住哪，或者根本不该留（很多东西不值得记）。四个去处，对应四种落地：

- **哪儿都不去（删/不记）**——git 历史里已有、别处已记录、只是一次性的顺带提及、或模棱两可的「说不定有用」。这类的正确动作是**不制造记忆**。强制的稀缺，正是让留下来的东西可信的原因。
- **某个 skill（作为改进）**——只关乎某个工具或流程的教训，属于那个 skill 内部。这是最常见、也最该走的去处：在那里它每次运行都改变行为，并像代码一样被版本管理。**下面「重构，而非追加」讲的就是这一路。**
- **预置（全局/项目 CLAUDE.md）**——只有同时跨领域、改变决策、几乎每轮都成立的才配。门槛极高；绝大多数「教训」都不该落在这里。
- **外部（文档）**——按需检索的参考知识。可以存，但要保持有链接、不过时。

一条 skill 专属的教训，若顺手也在预置里留一条面包屑，两份副本必然漂移——选一个家，别脚踏两只船。

## 第二步：重构，而非追加（落进 skill 时的核心功夫）

最好的学习让目标 skill 更清晰、更低噪、更好执行。一次好的更新改变的是 Agent 下次会遵循的**决策结构**：一张路由表、一个状态机、一份 checklist、一条触发规则、一个反例、或一段更利落的流程。它不是把原始资料剪贴进来的剪贴簿。

流程：

1. **命名未来的行为**——下一个 Agent 到底该做得有什么不同？说不出来，就还没提炼够。
2. **找到归属的 skill**——教训落在哪个 skill 的领域就更新哪个。只有当行为跨领域可复用、或压根没有归属者时，才新建 skill。
3. **诊断薄弱的决策点**——是什么让旧行为含糊？典型病灶：「这个请求该路由到哪」「什么时候该升级工具」「不该创建什么」「必须验证什么」。
4. **重构，别追加**——重写相关段落，让 skill 读起来是一份更好的操作指南。把描述同一个决策的段落合并；删掉或压缩被新结构取代的旧文字。
5. **保持表面最小**——几句话就该留在 SKILL.md；只有当细节可选、很长、依版本/场景而变、或大到塞不进主文档时，才值得新建一个 reference 文件。
6. **验证这次学习**——检查断链、私密信息、硬编码本地路径、行数漂移，以及是否需要同步更新插件 README / manifest 版本。

## 典型模式

- **低信息量的来源**——提炼一条原则或 2–3 个例子；不要照抄来源的目录结构。
- **工具/来源选择的教训**——用一张路由表胜过大段散文，因为它让执行变得明确。
- **用户纠偏**——更新那条放任了错误发生的触发条件或反模式，然后顺手简化附近的文字。
- **站点特定机制**——登录/浏览器细节留在操作型 skill 里；只有当步骤长到塞不下主文档时才拆到 references。
- **术语**——用领域原生的词。不要发明含糊的黑话，尤其是中英混杂的标签，除非生态里本来就这么叫。

## 反模式

- 因为来自不同笔记，就保留两段描述同一个决策的文字。
- 因为来源有小标题，就新建一个 reference 文件。
- 照抄一份报告的分类法，而其实一条规则就能改变行为。
- 往一个公开 skill 里塞进项目私有的名字、路径、案子、客户或环境假设。
