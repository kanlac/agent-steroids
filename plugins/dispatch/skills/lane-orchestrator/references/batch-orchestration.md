# 批次调度：编排表与多线长期并行

每个任务的模型和推理强度怎么选、怎么核对生效，按 dispatch skill 的模型与强度标准；本文只管多个任务放在一起时怎么排、怎么并行。

## 编排表

派出 4 个及以上 agent 时，选好模型和 effort 后汇成一张表向用户汇报。一行一个任务：

| 阶段 | 任务 | 执行者（模型 / 强度 / 派发方式） | 评审链 | 状态 |
|---|---|---|---|---|

- **执行者列写实际生效的配置。** 依据是启动配置或请求元数据，不是这张表或提示词；没有证据标「未验证」，确认被忽略标「未生效」（核对方法见 dispatch skill）。
- **实施与评审分列。** 评审链按先后列出每一级的模型 / 强度 / 方式，每级都要 PASS，标注轮次上限和
  「至少一个某模型循环至通过」这类硬要求。评审者与实施者来自不同厂商的模型。
- **状态**区分已定、待确认、试验。真正需要用户拍板的行标「待确认」并只阻塞这些行：花钱、产品方向、对外承诺、文案口径，未获授权的对外发布，以及缺账号、权限或用户设了检查点的；不与已定项混排。已获授权、依赖已满足的行汇报后即开跑，不因整张表没回复就全部停下。首次使用的模型标「试验」，
  并写清质量不达标时的升级路径和报告义务。

## 多线长期并行

几条线各占一个 worktree、跨多轮续做时，故障多出在共享的东西上，而不在单个任务里。

- **集成分支只由编排者动。** 「合入集成分支」会被读成让它自己合；要它吸收别人的改动就写「把集成分支合进你自己的分支」。合入的证据要在合并后的那棵树上取得，各自分支上通过不算。
- **每轮产物按轮编号，不覆盖。** CLI 写的最终回复与 agent 自己写的报告用不同文件名，报告也不进仓库，否则下一轮或下一个工具会把它盖掉。会话 ID 一并落盘，机器重启或进程被杀后靠它续做。收尾时只清可再生成、确认无后续依赖的大批中间产物；报告、评审、事件流、会话号和续跑所需材料保留。
- **吃满机器的活要在宿主上排队。** 全量测试、虚拟机、批量跑数据这类任务，各线同时起就互相拖垮。给它们一个宿主级的槽位：每个 worktree 同时最多占一个，排队时间不计入执行超时，占槽进程死了能自动回收。agent 会想办法绕过排队，正文里写明不许。车道数的上限由槽位和磁盘余量决定。
- **要在会话里等完。** 它留下后台任务就收工，会话一结束任务也跟着丢；排队等待的时间算在本轮里。一次只排自己下一步要用的活，不要一口气排几十个。
- **例外要在正文里显式授权。** 与常设规矩冲突的要求（如平时禁用的资源这次要用），不写明「这次允许」它会照旧拒绝，整轮白跑。
- **评审达标不等于没欠账。** 非阻塞的意见与「可选项」登记成账，下次改到同一文件时点名还掉；单次改动看着都可维护，几条线合起来可能出现重复和同类分支的累积，进主线前对全部改动整体再审一次。
